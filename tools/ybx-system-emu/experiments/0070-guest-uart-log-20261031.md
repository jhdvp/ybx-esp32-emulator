# 0070 — guest console: read the ESP32's own UART output, honestly

Date: 2026-10-31. Lane: batch-4 `guest-uart-log`. Scope: a standalone,
read-only module (`tools/ybx-system-emu/guest_console.py`) that tails one
QEMU serial chardev into a bounded ring buffer. The bridge itself was NOT
touched: `serve_x4pro_browser.py` still starts QEMU with all four serials on
null (`serve_x4pro_browser.py:492`, inside `_launch` at
`serve_x4pro_browser.py:485-498`); wiring the console in is the
orchestrator's decision, and this report gives the exact probe to do it.

## Why

A firmware image that never paints a frame currently produces zero evidence:
the operator sees "0 frames" and the guest's own boot ROM / bootloader / app
log is thrown away (`-serial null` x4). The console makes the guest's UART0
output readable while the guest runs, with bounded memory.

## What was added

### `guest_console.py`

- `RingBuffer` (`guest_console.py:93`): fixed-capacity byte buffer (default
  `DEFAULT_CAPACITY = 64 * 1024`, `guest_console.py:47`), lock-guarded,
  oldest bytes evicted first, `total_bytes` counts everything ever seen.
  Memory is hard-bounded: a guest stuck in a print loop cannot exhaust the
  bridge.
- `split_incomplete_utf8_tail` (`guest_console.py:70`): a UART stream stops
  mid-character all the time (and the ring edge cuts characters too). The
  helper separates the decodable prefix from a possibly-incomplete trailing
  sequence; `tail_text` (`guest_console.py:368`) drops the half character at
  the NEW edge (it may still arrive) and decodes bytes the ring already
  evicted as U+FFFD (they are genuinely gone).
- Two chardev backends (pick one when starting QEMU):
  - `UnixSocketChardevSource` (`guest_console.py:190`) — **primary,
    documented choice**. Start QEMU with
    `-serial unix:PATH,server=on,wait=off -serial null -serial null -serial
    null` (replace only the FIRST `-serial`; on the esp32s3 machine UART0 is
    the first serial, and that is where the ROM prints). QEMU is the
    listening server, the console connects as a client. `wait=off` keeps QEMU
    booting with no console attached; bytes printed while disconnected are
    LOST. After the first connection a dropped stream (QEMU quit, guest
    relaunched) is retried for `reconnect_grace` s; past that the stream is
    ENDED — this is how the guest that SIGSEGVs QEMU terminates the console
    instead of spinning (`guest_console.py:196,244-254`).
  - `FileChardevSource` (`guest_console.py:133`) — fallback for the Docker
    host boundary: `-serial file:PATH`, QEMU appends, the console follows the
    growing file from the Mac. Re-detects a truncated file (guest relaunch,
    `guest_console.py:170`). A unix socket on a Docker Desktop bind mount was
    NOT tested and is not assumed to work; the file backend was (see below).
- `GuestConsole` (`guest_console.py:298`): daemon reader thread
  (`_pump`, `guest_console.py:322`) feeding the ring; `tail()`/`tail_text()`
  are cheap snapshots safe from any thread (the HTTP handler); `wait_for()`
  (`guest_console.py:375`) for probes; `stop(timeout=2.0)` (`:339`). It never
  writes to the source — the console is read-only toward QEMU.
- CLI (`main`, `guest_console.py:389`):
  `python3 guest_console.py --socket PATH --duration 45` or
  `--file PATH --until 'entry 0x' --max-wait 90`; prints the decoded tail to
  stdout, exit 0 on data/end, 2 on never-connectable chardev.

## What the console shows — and what it plainly cannot show

Demonstrated value, from the captures above:

1. The ROM + second-stage-bootloader handshake of any flashed image becomes
   readable while the guest runs (all four images: boot mode
   `SPI_FLASH_BOOT`, the three loader segments, `entry 0x403c8898`).
2. Guest death is distinguishable from guest silence: the CrossPoint-2.0.0rc
   SIGSEGV produced "stream ended" and flushed the last bytes; factory and
   expA produced a timeout exit with an alive stream.

Limits, stated plainly:

- **None of these four firmware images prints anything on UART0 after
  `entry 0x403c8898`.** The factory home screen paints (accepted frame
  `e79c2ad5…`) with zero app log on UART0/1/2 — its ESP-IDF log level or
  USB-Serial-JTAG routing simply never reaches an emulated serial. The
  console cannot show output the firmware does not produce; for this family
  of images the UART tail is a boot handshake + crash detector, NOT an app
  log.
- Because of that, **the console alone cannot distinguish "hangs" from
  "boots and is quiet"**: the factory and expA captures are byte-identical.
  It narrows the diagnosis (loader ran, app went silent) but the operator
  still needs `/api/state` frames/boot flags for the verdict.
- A guest that dies before UART is configured, or writes only to registers
  the model ignores, prints nothing (same as on real hardware).
- With `server=on,wait=off` bytes written while no client is connected are
  lost, and a reconnect cannot recover them; QEMU does not buffer. For a
  guaranteed capture attach the console before launch, or use the `file:`
  backend, which keeps everything QEMU wrote from the start.
- Older output beyond 64 KiB is evicted (by design); the CLI reads at most
  4 KiB per poll with a 0.1 s cadence, so a very chatty guest overflows the
  ring quickly — the tail is still correct, just short.
- Emulated UART timing/baud accuracy was not measured; bytes arrive in
  stream order but not with real-world inter-byte timing guarantees.

## Probe script for the orchestrator

Save as `run_guest.sh` in a host scratch dir mounted at `/out` (it writes
`/out/$LABEL-uart.log` and `/out/$LABEL-console.err`), mount the lane's
`tools/ybx-system-emu` read-only at `/tests`:

```bash
#!/usr/bin/env bash
# Run one throwaway QEMU guest (socket chardev on UART0) and capture the
# guest's own UART output with guest_console.py. Everything happens inside a
# fresh `docker run --rm` container; nothing here touches the live bridge.
set -eu
DUR="${DUR:-45}"
mkdir -p /tmp/rom
cp /work/s3-full-rom-generator-test.bin /tmp/rom/esp32s3_rev0_rom.bin
cp "$FLASH" /tmp/flash.bin
cp /work/ybx-test-sd-fat16-mbr-pristine.img /tmp/sd.img
/qemu/build-ybx/qemu-system-xtensa \
  -machine esp32s3,ybx-x4pro-i2c=on,ybx-x4pro-gt911=on,ybx-x4pro-sd-power=on,ybx-x4pro-spi2=on,ybx-x4pro-epd=on \
  -m 8M -global ssi_psram.is_octal=on \
  -nographic -monitor none \
  -serial "unix:/tmp/guest0.sock,server=on,wait=off" \
  -serial null -serial null -serial null \
  -qmp unix:/tmp/qmp.sock,server=on,wait=off \
  -L /tmp/rom \
  -drive file=/tmp/flash.bin,if=mtd,format=raw \
  -drive file=/tmp/sd.img,if=sd,format=raw \
  >/tmp/qemu.out 2>/tmp/qemu.err &
QPID=$!
timeout $((DUR + 60)) python3 -u /tests/guest_console.py \
  --socket /tmp/guest0.sock --duration "$DUR" >"/out/$LABEL-uart.log" 2>"/out/$LABEL-console.err"
cat "/out/$LABEL-uart.log"
kill "$QPID" 2>/dev/null || true
wait "$QPID" 2>/dev/null || true
```

Inside the bridge the integration is one-sided and small: in `_launch`
(`serve_x4pro_browser.py:485-498`) replace the first `"-serial","null"` with
`"-serial",f"unix:{t/'guest0.sock'},server=on,wait=off"`, then
`gc.GuestConsole(gc.UnixSocketChardevSource(t/'guest0.sock')).start()` and
expose `console.tail_text(N)`. Both the socket and the reader live inside the
same container as QEMU, so no host↔container socket question arises. That
edit belongs to the orchestrator's lane and was deliberately not made here.

## Unproven after this lane

- No live-bridge wiring: the running `ybx-x4pro-browser-8784` container and
  `serve_x4pro_browser.py` are untouched; an HTTP surface for the tail does
  not exist yet.
- Whether a quieter/foreign ESP-IDF app that DOES log to UART0 exists in the
  firmware folder was not tested beyond the four images above (crosspoint
  1.6.5, inkMOD, the `ybx-settings` build were not run).
- Host-side unix-socket attach across the Docker bind mount: not attempted
  (deliberately; the file backend is the documented cross-boundary path and
  was exercised).
- Baud/character-level fidelity of the emulated UART: not measured.
