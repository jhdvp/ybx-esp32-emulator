## Question

Upstream CrossPoint publishes **one image per board** (`x3-x4`, `x4c`, `x4pro`,
`sticky`, `picco`, `metalio_eink4`, `papermono`, `eego_a4`) and inkMOD publishes
`x4pro`, `x4classic`, `x3x4`. The emulator models **one machine**: ESP32-S3 with
an SSD1677 800x480 1bpp panel wired to the pins the X4 Pro uses. Does the rest
of the family run on it, and if not — what exactly is missing?

Two facts fall out of the bytes alone:

* **None of the 16 published assets is a flash image.** All are app-only: magic
  `0xE9` at `0x0`, no partition-table magic `0xAA50` at `0x8000`. That is exactly
  why the bridge refuses them (the same three rules as

  x3/x4 envs and `board_build.mcu = esp32s3` for the S3 envs
  (`platformio.ini:354-355,393-395,...`).

## 2. The merge rule, reproduced byte-for-byte

`build_flash_image` (panel_matrix.py:236-258) implements what
`firmware/README.txt` states: X4 Pro base head at `0x0` (bootloader), partition
table at `0x8000`, application at `0x10000`, the rest of the 16 MiB filled with
`0xFF` (erased flash). The head is taken from
`firmware/crosspoint-2.0.0rc-x4pro-flash-16m.bin` and pinned by SHA-256
(`X4PRO_BASE_HEAD_SHA256 = 7c89d75bdb8858a4…`, panel_matrix.py:64-70); the same
64 KiB appear in the 1.6.5 and inkMOD images there.

Real check, not a claim — rebuilding the three shipped images from a downloaded
asset plus the pinned head:

```
head len 65536 sha 7c89d75bdb8858a4
crosspoint-2.0.0rc-x4pro-flash-16m.bin True 16777216
crosspoint-1.6.5-x4pro-flash-16m.bin   True 16777216
inkmod-v1.1.10-x4pro-flash-16m.bin     True 16777216
```

(`ReproductionTest.test_merged_image_equals_the_shipped_one` pins this in the
suite.) An image is byte-identical to the operator's file, so the merge step
adds no variable to the boot results: any difference below comes from the guest,
not from the packing.

A note on offsets: the app always lands at `0x10000` because that is where the
**X4 Pro** partition table puts `app0` (`partitions.csv`: `app0 … 0x10000
0x640000`). A board's own layout is deliberately not preserved — e.g. Picco
installs into `app ota_0` at `0xE0000` inside the stock `partitions_picco.csv`
(`partitions_picco.csv:6-9`). That is legal for a boot attempt (the ESP loader
relocates the segment load addresses to the partition the image is read from),
but it is a real difference a per-board machine would have to model.

What the emulator hard-codes today, in the live kernel:

* geometry is a **compile-time macro**: `YBX_EPD_WIDTH 800`,
  `YBX_EPD_HEIGHT 480` (`include/hw/display/ybx_ssd1677.h:9-10`);
* the pin map is **wired in the machine**, not parameterised: GPIO13→CS,
  GPIO18→DC, GPIO14→RESET, BUSY→GPIO6 (`hw/xtensa/esp32s3.c:1008-1022`), GT911
  on 39/38/10/4 (`hw/xtensa/esp32s3.c:996-1004`);
* the device is a single SSD1677 command set
  (`hw/display/ybx_ssd1677.c:1-3` — "800x480 1bpp", not a waveform model).

So the machine property each board would need is, concretely:

| board | missing machine property |

| x4pro | none — it is the modelled machine |
| x4c | EPD `dc`/`rst`/`busy` pin overrides (14/10/18 vs 18/14/6), touch off |
| sticky | full EPD pin remap (13..18), a second I2C bus for GT911 (3/2), EPD power pin 47, PSRAM off |
| picco | EPD pin remap (48/47/18/17/16/15), 20 MHz SPI2, an UltraChip/SSD2677 device with active-low BUSY and a 2 bpp plane, app partition 0xE0000 |

| papermono | EPD pin remap (15/14/16/17/18), ROTATE_180 scan, M5IOE1 expander for reset/power, FT6336 device |

## 6. Honest conclusion

Filled by the orchestrator on 2026-11-01 from the §4 table (the lane was cut off
before writing it).

1. **Only images built for this board paint.** 2 of 17 rows produced frames —
   `crosspoint-2.0.0rc-x4pro` and `crosspoint-1.6.5-x4pro`, both byte-identical
   to the shipped artifacts. The other fifteen are `painted nothing`, and that
   is expected, not a regression: the machine hard-codes X4 Pro's pin map, its
   800x480 geometry as a compile-time macro, GT911 on 39/38/10/4 and BUSY on
   GPIO6.
2. **Two different reasons hide behind one verdict.** The `x3-x4` / `x3x4`
   assets are ESP32-C3 firmware (`chip_id 0x0005`) — no amount of panel work
   makes them run on an `esp32s3` machine; they would need a second machine
   type. The six S3 siblings (x4c, sticky, picco, metalio_eink4, papermono,
   eego_a4) are the right SoC and fail on wiring: every one of them drives a
   different GPIO set (§5), and three also differ in controller command set,
   BUSY polarity, rotation or framebuffer size.
3. **inkMOD is the row that actually costs us something.** Its `x4pro` build is
   the correct chip and the correct board and still paints zero frames, which
   is why the panel matrix stays green as a *measurement* tool: it separates
   "wrong board" from "our model is missing a behaviour". The stop point for
   that one is in `probe_x4pro_inkmod_trace.py` (IPC/RTC sleep handshake), not
   in the display.
4. **Cheapest path to a second board** is not a new device model: make
   `width/height`, the six EPD GPIOs, the BUSY polarity and the touch pins
   machine properties on the existing SSD1677 device, which would cover x4c,
   sticky and metalio_eink4 immediately. `picco` (UltraChip "SSD2677" command
   set), `papermono` (ROTATE_180 + IOE expander) and `eego_a4` (UC8279C,
   768x552, BUSY active-low) each need real driver work, and `x3-x4` needs an
   ESP32-C3 machine. Until someone asks for a specific device, the emulator
   stays single-board and says so.
